# classic Quest teleoperation feature inventory

> Public copy: local paths, device identifiers and site addresses are anonymized; recorded test results and version information are retained.

## Scope and classification criteria

This is a read-only inventory of `/path/to/unity/classic`, with snapshot date 2026-09-16. The following were examined:

- `Assets/Scripts` (including `New`, `MultipleVideoStream`, `TCP`, `Force`, `Tactile Visualization`, `UpperLimb`, `VirtualRobot`, `Unused`, `Viz`);
- `Assets/Editor/TactARSceneSetup.cs`;
- Serialized objects, parent-child relationships, and `UnityEvent` in `Assets/Scenes/V0.6.0 Realtime_Force.unity` and `Assets/Scenes/V0.7.0 Upper Limb.unity`;
- `Assets/Prefabs/Canvas.prefab` and related arrow/tactile prefabs;
- `Assets/Settings/TeleopConfigUpperLimb.asset`.

The three labels in this document mean:

- **Active scene wiring**: active components, references, object states, or button events already serialized in the V0.6/V0.7 scenes. Objects whose panels are initially inactive but enabled on demand by a wired manager are also listed here.
- **Runtime auto-created**: the scene has no serialized component; code creates it or completes wiring in `Awake`, `Start`, or `[RuntimeInitializeOnLoadMethod]`. Refactoring cannot rely solely on scene YAML migration.
- **Unused legacy**: neither current target scene has an active reference, the object is explicitly inactive, or it exists only in historical scenes/commented code. Visible effects and protocols are still recorded to avoid accidentally deleting paths still used by users or external robots.

No writes were made to classic apart from this document; no Editor menu commands that save scenes were run. The only actual scene differences are that V0.7 adds Upper Limb AKM components and three UI child objects, plus a Panel alpha change; V0.6's `UpperLimbAkmBootstrap` still supplies the AKM manager/UI at runtime, but the scene has no corresponding buttons.

## Configuration, prefabs, and protocol essentials

### `TeleopConfigUpperLimb.asset` and actual runtime defaults

`Assets/Settings/TeleopConfigUpperLimb.asset` serializes: `defaultServerIP=192.0.2.16`, pose 8001, control 8005, virtual robot 8011, tactile 8012, signaling 8765, UDP video base 8000, default WebRTC track 1, send rate 30, binary=1, and all three safety bools set to 1.

Both target scenes' `AppManager.teleopConfig` are `{fileID: 0}`. Consequently, `AppManager.ApplyConfigDefaults()` does not read this asset; actual initial IP is the code field's `192.0.2.11`, and other ports retain code fields 8001/8005/8012/8765/8000; `PreventSleep`, tracking pause, and recalibrate also use `true` because config is null. These are behavioral facts, not inferences from the asset.

`PlayerPrefs` load in `AppManager.Start` via `LoadConfig()`, so existing `cfg_ip`, mode, rate, binary, and track count on old devices override these initial values. Migration must decide whether to connect the asset while preserving old PlayerPrefs priority or explicitly support the existing hardcoded fallback.

### `Canvas.prefab` (GUID `14d06f2d739b37549abe5c5d3e780fe8`)

This is the prefab actually referenced by `UdpWindowManager.udpWindowPrefab`, rather than merely a RawImage:

- Root `Canvas` has `VideoWindowController` (script GUID `e7d67a6de85fee54690a2da32347c7a9`), wired to close, port input, `ZOOM Button`, resolution label, status;
- Root also has the disabled old `DraggableWindow`, but active `RawImage` has `DraggableWindowWorld` targeting root Canvas;
- `Plane` child has `UdpSocketMultiHD` and mesh/renderer; receive IP/port supplied at runtime by `Initialize`;
- World-space Canvas, GraphicRaycaster, TrackedDeviceRaycaster, BoxCollider/Rigidbody provide interaction foundations; default input text is `PORT`, default resolution label `x1.0`.

The HD receiver must retain the 12-byte big-endian chunk header, maximum 8 frame buffers, duplicate-chunk ignoring, and completed frames returned to main thread. It has no scene-configured port and depends entirely on `VideoWindowController.Initialize`.

## Migration priorities and main risks

1. **The disconnected configuration asset is the primary risk.** Scene `teleopConfig=0`, runtime IP `192.0.2.11`, while the asset in the same directory contains `192.0.2.16`. Binding the asset directly in a new AppManager changes the first-run destination; migrating only scene wiring leaves asset safety/port fields permanently ineffective. Define clear priority among old PlayerPrefs, asset, and code fallback, and perform an upgrade acceptance check on an old device.
2. **Port ownership for 8012/8005 requires explicit design.** Current 8012 belongs to active `TCPPoseReceiver`, `ForceSensorReceiver` on 8013 is inactive, and VideoWindowManager tactile reception is disabled; 8005 is potentially shared by AppManager control, V0.7 WRM, and old window resolution. Restoring Focus UI or WRM without arbitration causes parsing conflicts/packet loss/duplicate states.
3. **The safety gate is a shared sender precondition.** `DualControllerSender` and `HandTrackingSender` both depend directly on `AppManager.CanSendTeleopData`; tracking lost, recalibration, or Stopping must each prohibit sending. New UI Start/state implementation must not simply change text while bypassing `NeedsRecalibration`.
   `UpperLimbAkmManager` is a verified exception: its WRM loop checks only `WrmEnabled`, so any behavior change from a unified safety gate must be explicitly recorded in migration decisions and regression checks.
4. **Scene wiring comes from more than field references.** Control mode, recording, exit, IP, Add UDP, reposition, and others have persistent `UnityEvent`; AppManager also adds listeners only to nonempty fields. In particular, `controlModeButton=0` but the scene event still works; UI migration can easily yield visible buttons with no call, or duplicate calls.
5. **V0.6/V0.7 WRM lifecycles differ.** V0.7 has serialized manager/UI/buttons; V0.6 relies on bootstrap, can run only in background, and UI cannot find objects. New scenes must avoid separate copies from bootstrap and scene objects, and synchronize WRM shutdown in Hands mode.
6. **Coordinate transforms cannot be rewritten by intuition.** Mirror automatic yaw/manual 6DoF and View robot-base transforms have translation/quaternion axis swaps and sign conventions; TCP/force belong to Calibration subtree and move with parent during calibration. Validate using fixed-pose packet golden values, not visual alignment alone.
7. **Timing and threading semantics are part of the protocol.** Controller 100 Hz catch-up limits, scene Hand 60 Hz text protocol, WRM 30 Hz JSON, and UDP-frame chunks received on background threads with main-thread texture updates affect both robot and Quest performance. New UI/session layers must not unify them into one unverified Update rate.
8. **Enabling WebRTC destroys UDP windows.** It calls `CloseAllWindows()` and disables Add UDP; creation resumes only after disabling WebRTC. Retain both side effects: video failure does not affect teleop, and window types are mutually exclusive; otherwise users may see video while pose transmission has unexpectedly stopped.
9. **Actual UDP-window interaction comes from the prefab.** `VideoWindowController`, active `DraggableWindowWorld`, HD receiver, and `ZOOM Button` are absent from the target scene's custom-component table and would be missed by scene-only migration; prefab also includes disabled old `DraggableWindow`, so do not incorrectly enable both drag handlers.
10. **Focus/zoom works locally while network wiring is absent.** Each window's zoom label currently cycles, but FocusModeButton/Label are null, so old resolution messages are not sent. Reconnecting Focus in new UI requires separate regression of right A versus WRM calibrate A conflicts and the 8005 message protocol.
11. **TCP force and historical tactile displays have different inputs.** Current primary path is combined TCP+force JSON on 8012; historical 41-point tactile also used 8012 and was explicitly disabled by Editor tool. Re-enabling its listener to retain tactile would directly break current RightTCP/RightForce.
12. **`RobotTcpAxes` has Editor intent only, without scene evidence.** `TactARSceneSetup` comments say axes are added, but neither target scene contains the script GUID. Migration acceptance should treat TCP red/green/blue axes as an explicit product choice instead of assuming they are active.
13. **Static/runtime state is not inherently persistent across scenes.** The combination of `TeleopReferenceFrame`, `TeleopControlModeManager.CurrentMode`, robot-base anchor, and PlayerPrefs is affected by scene/domain reload; stopping streaming clears frame, and restarting reads configuration again. Verify cleanup ordering for reload, stop, and tracking loss in the new lifecycle.
14. **The VR keyboard is an input submission protocol, beyond its visual component.** It deliberately bypasses the Quest system keyboard and TMP editing state, explicitly invoking `onEndEdit` only on Enter/outside click; replacing it with ordinary `ActivateInputField` causes IP-saving and Quest-interaction regressions.
15. **Recording state is inferred from text.** External recorder receives only `Start`/`Stop`, with button text the sole source of state; any new UI label, translation, or initial-value change affects the next command. Refactor may add internal boolean state, but retain `Recording()` and exact commands for old scene events.
16. **Inactive custom Passthrough must not be enabled accidentally.** The scene's Meta Passthrough Building Block is active, which does not imply `PassthroughToggle` is wired; all its refs are empty, and direct activation throws. Treat it as explicit opt-in.

## Minimum end-to-end regression sequence

Before announcing the new app as a replacement for classic, run equivalent V0.6 and V0.7 scenes in this order: launch and confirm no duplicate runtime objects; enter IP/1..3 tracks and restart; capture C packets in Controllers mode; capture H packets in Hands mode; start/stop streaming; trigger tracking lost→recovery→recalibration; Mirror/View and two-stage base placement; V0.7 two-stage WRM calibration and 8005 JSON; 8012 TCP/force JSON; create, drag, zoom, B/Y layout, and close UDP windows; WebRTC 1/2/3-track toggling and failure degradation; recording Start/Stop; collapsible menu, manual, VR keyboard; finally Quit and optional legacy fallback. At every step, examine UI state, port captures, and exceptions on the Quest main thread together.
